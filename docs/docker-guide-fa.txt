===============================================================================
  راهنمای Docker برای پروژهٔ ERP
  فایل‌های مرتبط:  deploy/docker-compose.yml ، deploy/Dockerfile ، deploy/.env
===============================================================================


۰) داکر در سه جمله
-------------------------------------------------------------------------------
«ایمیج» یک بستهٔ آمادهٔ نرم‌افزار است (مثل فایل نصب).
«کانتینر» یک نسخهٔ در حال اجرا از آن ایمیج است (مثل برنامهٔ نصب‌شده و باز).
«compose» فایلی است که می‌گوید چند کانتینر با چه تنظیماتی کنار هم اجرا شوند.

در این پروژه از داکر فقط برای Redis و MongoDB (و Postgres که فعلاً بی‌استفاده
است) استفاده می‌شود. دیتابیس اصلی یعنی SQL Server روی خود ویندوز نصب است و
داخل داکر نمی‌آید.


۱) دستورهایی که لازم داری
-------------------------------------------------------------------------------
همهٔ دستورها را داخل پوشهٔ deploy اجرا کن.

  بالا آوردن فقط دیتابیس‌ها (حالت عادی توسعه):
      docker compose up -d

  دیدن وضعیت:
      docker compose ps

  دیدن لاگ یک سرویس:
      docker compose logs -f redis

  خاموش کردن (داده‌ها می‌مانند):
      docker compose down

  خاموش کردن و پاک کردن کامل داده‌ها:
      docker compose down -v          ← احتیاط: دیتابیس‌ها خالی می‌شوند

  بالا آوردن خود برنامه هم به‌همراه دیتابیس‌ها:
      docker compose --profile app up -d --build

  بازسازی ایمیج برنامه بعد از تغییر کد:
      docker compose --profile app build api
      docker compose --profile app up -d api

نکته: سرویس api داخل یک «profile» به نام app گذاشته شده. یعنی با
«docker compose up -d» معمولی بالا نمی‌آید و فقط دیتابیس‌ها روشن می‌شوند —
همان کاری که تا امروز می‌کردی. هر وقت خواستی برنامه هم داخل داکر اجرا شود،
--profile app را اضافه کن.


۲) سرویس‌ها و اینکه برنامه واقعاً از کدام‌شان استفاده می‌کند
-------------------------------------------------------------------------------
SQL Server              ← دیتابیس اصلی. داخل داکر نیست: از موتور SQL Server
                          که روی خود ویندوز نصب است استفاده می‌شود.
                          کد پروژه صراحتاً همین را می‌خواهد
                          (UseSqlServer در ERP.Infrastructure/ConfigureServices.cs)

redis       پورت 6379   ← کش و رمزهای یک‌بارمصرف (OTP)
                          استفاده می‌شود در CacheDbContext و OneTimePasswordService

mongo       پورت 27017  ← مقصد لاگ‌های Serilog

postgres    پورت 5432   ← فعلاً هیچ کدی به آن وصل نمی‌شود.
                          نگه داشته شد چون گفته بودی نظرت PostgreSQL است و
                          ممکن است بعداً کد به آن منتقل شود. اگر تصمیم گرفتی
                          روی SQL Server بمانی، این سرویس را حذف کن.

mariadb                 ← حذف شد. هیچ ارجاعی در کل کدبیس نداشت.


۳) کامنت‌هایی که از docker-compose.yml برداشته شد
-------------------------------------------------------------------------------
به درخواست تو همهٔ کامنت‌ها از فایل compose پاک شدند. محتوای مفیدشان اینجاست:

  POSTGRES_USER        نام کاربری postgres
  POSTGRES_PASSWORD    رمز عبور postgres
  POSTGRES_DB          نام دیتابیسی که هنگام اولین اجرا ساخته می‌شود

  (مربوط به mariadb که حذف شد)
  MYSQL_ROOT_PASSWORD  رمز کاربر root
  MYSQL_DATABASE       دیتابیس اولیه که خودکار ساخته می‌شد
  MYSQL_USER           یک کاربر معمولی غیر از root
  MYSQL_PASSWORD       رمز همان کاربر

توضیح متغیرهای جدید که اضافه شدند:

  SQLSERVER_HOST         آدرس موتور SQL Server روی ویندوز، آن‌طور که از داخل
                         کانتینر دیده می‌شود. مقدار host.docker.internal یک نام
                         ویژهٔ داکر است که به خود ماشین میزبان اشاره می‌کند.
                         فقط وقتی استفاده می‌شود که برنامه داخل داکر اجرا شود.

  SQLSERVER_DB           نام دیتابیس برنامه.

  SQLSERVER_USER
  SQLSERVER_PASSWORD     ⚠ باید یک لاگین SQL Authentication باشد. احراز هویت
                         ویندوزی (Trusted_Connection) از داخل کانتینر لینوکسی
                         کار نمی‌کند. بخش ۶ را ببین.

  JWT_KEY                کلید امضای توکن. حتماً قبل از هر استقرار واقعی عوض شود.


۴) فایل .env
-------------------------------------------------------------------------------
همهٔ رمزها از فایل compose بیرون کشیده شدند و داخل deploy/.env قرار گرفتند.
دو فایل داری:

  deploy/.env           فایل واقعی که compose می‌خواند. رمز دارد.
                        به .gitignore اضافه شد تا هرگز کامیت نشود.

  deploy/.env.example   الگو. بدون رمز واقعی، قابل کامیت. هر کسی پروژه را
                        clone کند، از روی این یکی .env خودش را می‌سازد:
                            cp deploy/.env.example deploy/.env

مقادیر پیش‌فرض عمداً ساده‌اند تا خودت با دادهٔ واقعی جایگزین کنی.


۵) فایل Dockerfile — خط به خط
-------------------------------------------------------------------------------
این فایل می‌گوید چطور از روی کد، یک ایمیج قابل اجرا ساخته شود.
دو مرحله دارد که به آن «multi-stage build» می‌گویند.

  مرحلهٔ اول (build) — با ایمیج SDK که کامپایلر دارد:

    COPY ... *.csproj        فقط فایل‌های پروژه کپی می‌شوند، نه کل کد
    RUN dotnet restore       پکیج‌های NuGet دانلود می‌شوند

    چرا اول فقط csproj؟ چون داکر هر مرحله را کش می‌کند. تا وقتی فایل‌های
    csproj عوض نشده‌اند، دانلود پکیج‌ها دوباره انجام نمی‌شود. اگر از اول کل
    کد را کپی می‌کردیم، با هر تغییر کوچک در کد، همهٔ پکیج‌ها دوباره دانلود
    می‌شدند و هر بیلد چند دقیقه طول می‌کشید.

    COPY src/ src/           حالا کل کد کپی می‌شود
    RUN dotnet publish       کامپایل در حالت Release داخل /app

  مرحلهٔ دوم (runtime) — با ایمیج aspnet که فقط اجراکننده است، بدون کامپایلر:

    COPY --from=build /app   فقط خروجی کامپایل‌شده از مرحلهٔ قبل برداشته می‌شود
    RUN mkdir /app/Logs      پوشهٔ لاگ ساخته و دسترسی نوشتن داده می‌شود
    USER $APP_UID            برنامه با کاربر غیر-root اجرا می‌شود (امنیت)
    EXPOSE 8080              پورتی که برنامه داخل کانتینر گوش می‌دهد
    ENTRYPOINT dotnet ...    دستوری که هنگام روشن شدن کانتینر اجرا می‌شود

  نتیجه: ایمیج نهایی فقط شامل ایمیج runtime و خروجی publish است. کد منبع،
  کامپایلر و پکیج‌های NuGet داخلش نیستند — یعنی ایمیج چند برابر کوچک‌تر و
  امن‌تر می‌شود.

فایل .dockerignore در ریشهٔ پروژه می‌گوید چه چیزهایی اصلاً به داکر فرستاده
نشوند: پوشه‌های bin و obj، .git، پوشهٔ تست، مستندات. بدون آن، صدها مگابایت
فایل بی‌مصرف در هر بیلد جابه‌جا می‌شود.


۶) دیتابیس اصلی: SQL Server روی ویندوز
-------------------------------------------------------------------------------
SQL Server داخل داکر نیست. برنامه به همان موتوری وصل می‌شود که روی ویندوز
نصب است. این یعنی:

  ● حالت عادی (برنامه با dotnet run روی ویندوز اجرا می‌شود)
    هیچ تغییری لازم نیست. کانکشن‌استرینگ فعلی در appsettings.Development.json
    همین حالا درست است:
        Data Source=.\MSSQLSERVER2022;Database=ERP_DB_Development;
        Trust Server Certificate=true;Trusted_Connection=True;
    فقط کافی است یک‌بار مایگریشن اجرا شود تا جدول‌ها ساخته شوند:
        dotnet ef database update --project src/infrastructure/ERP.Infrastructure
                                  --startup-project src/infrastructure/ERP.Infrastructure

  ● حالت داکری (اگر بعداً با --profile app برنامه را داخل داکر اجرا کنی)
    اینجا سه نکته هست:

    ۱. آدرس: از داخل کانتینر، «localhost» یعنی خود کانتینر نه ویندوز. برای
       رسیدن به ویندوز باید host.docker.internal استفاده شود که در فایل
       .env تنظیم شده است.

    ۲. احراز هویت: Trusted_Connection (احراز هویت ویندوزی) از داخل کانتینر
       لینوکسی کار نمی‌کند. باید در SQL Server یک لاگین SQL Authentication
       بسازی و در .env بگذاری:

           CREATE LOGIN erp_app WITH PASSWORD = 'یک رمز قوی';
           USE ERP_DB;
           CREATE USER erp_app FOR LOGIN erp_app;
           ALTER ROLE db_owner ADD MEMBER erp_app;

       همچنین باید SQL Server در حالت Mixed Mode باشد (SQL Server
       Management Studio ← Properties ← Security ← SQL Server and
       Windows Authentication mode) و بعدش سرویس ری‌استارت شود.

    ۳. پورت و فایروال: نمونهٔ نام‌دار MSSQLSERVER2022 به‌صورت پیش‌فرض روی
       پورت ثابت ۱۴۳۳ گوش نمی‌دهد. در SQL Server Configuration Manager
       باید TCP/IP فعال و پورت ۱۴۳۳ ثابت شود، و فایروال ویندوز اجازهٔ
       ورودی روی آن پورت را بدهد.

    تا وقتی برنامه را روی ویندوز اجرا می‌کنی، هیچ‌کدام از این سه لازم نیست.

توجه: مایگریشن فعلی (InitialCreateDatabase) برای SQL Server ساخته شده است.
اگر بعداً تصمیم گرفتی به PostgreSQL بروی، باید کد به UseNpgsql تغییر کند و
مایگریشن از نو ساخته شود.


۷) تغییرات دیگری که در این پاس انجام شد
-------------------------------------------------------------------------------
- انکدینگ فایل compose از UTF-16 به UTF-8 تبدیل شد. قبلاً git diff و هر ابزار
  غیرویندوزی محتوای فارسی را خراب نشان می‌داد.

- restart: always  →  restart: unless-stopped
  با always، کانتینرها با هر ریستارت ویندوز خودکار بالا می‌آمدند حتی اگر
  خودت خاموششان کرده بودی. با unless-stopped، اگر دستی متوقفشان کنی متوقف
  می‌مانند.

- volume مربوط به redis که تعریف شده بود ولی به سرویس وصل نبود، وصل شد و
  appendonly روشن شد. قبلاً با حذف کانتینر، تمام داده‌های Redis از جمله
  کدهای یک‌بارمصرف از بین می‌رفت.

- به هر سرویس healthcheck اضافه شد. حالا داکر می‌داند یک دیتابیس واقعاً
  آمادهٔ پاسخگویی است یا فقط پروسه‌اش روشن شده. سرویس api با
  depends_on: condition: service_healthy منتظر آماده شدن آن‌ها می‌ماند.

- نام کانتینرها یکدست شد: erp-postgres ، erp-redis ، erp-mongo ، erp-api.
  نام پروژهٔ compose هم «erp» تعریف شد (قبلاً داکر از نام پوشه یعنی «deploy»
  استفاده می‌کرد).

- همهٔ ایمیج‌ها به نسخهٔ دقیق پین شدند، نه تگ latest و نه فقط شمارهٔ major:

      postgres:17.10
      redis:8.8.0
      mongo:8.3.11
      mcr.microsoft.com/dotnet/sdk:10.0.401      (در Dockerfile)
      mcr.microsoft.com/dotnet/aspnet:10.0.12    (در Dockerfile)

  چرا؟ با تگ latest یا حتی با تگ major مثل redis:8، ماه بعد ممکن است
  نسخهٔ دیگری زیر همان تگ بنشیند و رفتار سیستم عوض شود بدون اینکه یک خط
  کد تغییر کرده باشد. با نسخهٔ دقیق، هر ماشین و هر زمان همان ایمیج را
  می‌گیرد. برای به‌روزرسانی، شماره را عمداً و آگاهانه در این فایل عوض کن.

  نکتهٔ مفید: تگ گذاشتن روی یک ایمیج موجود (docker tag) هیچ دانلودی لازم
  ندارد و کپی هم نمی‌کند؛ فقط یک نام تازه به همان Image ID می‌دهد. اگر
  دیجست ایمیج محلی با دیجست همان تگ در رجیستری یکی باشد، می‌شود بدون
  دانلود آن را تگ کرد. بررسی‌اش:
      docker image inspect <image> --format '{{index .RepoDigests 0}}'
      docker buildx imagetools inspect <tag> --format '{{.Manifest.Digest}}'

۱۰) سه ایرادی که این تست‌ها در خود برنامه پیدا کرد
-------------------------------------------------------------------------------
این‌ها ربطی به داکر ندارند ولی بدون اجرای واقعی معلوم نمی‌شدند.

  الف) در محیط Production اتصال به MongoDB اجباراً TLS می‌شود
       فایل: ERP.WebApi/ConfigureServices.cs
           if (environment.IsProduction()) { mongoClientSettings.UseTls = true; }
       یعنی هر استقرار واقعی باید MongoDB با TLS داشته باشد، وگرنه برنامه
       اصلاً بالا نمی‌آید. چون compose یک استک توسعهٔ محلی است،
       ASPNETCORE_ENVIRONMENT روی Development گذاشته شد.

  ب) برنامه هیچ‌وقت به MongoDB احراز هویت نمی‌فرستد
       فایل: ERP.WebApi/ConfigureServices.cs
           //Credential = MongoCredential.CreateCredential(database, user, pass),
       این خط کامنت شده است. پس User و Password در appsettings خوانده
       می‌شوند ولی استفاده نمی‌شوند. به همین دلیل سرویس mongo در compose
       بدون رمز بالا می‌آید — اگر رمز داشته باشد، برنامه کرش می‌کند.
       ⚠ برای محیط عملیاتی این خط باید فعال شود.

  ج) اتصال به MongoDB در لحظهٔ استارت انجام می‌شود و شکستش کشنده است
       AddLogServices هنگام بالا آمدن ایندکس می‌سازد. اگر Mongo در دسترس
       نباشد، کل برنامه کرش می‌کند — برخلاف سرویس‌های پس‌زمینه که خطا را
       می‌گیرند و بک‌آف می‌کنند (این رفتار درست تست و تأیید شد: با
       در دسترس نبودن SQL Server برنامه بالا ماند و فقط لاگ خطا داد).


۱۱) نکته دربارهٔ مستندسازی API
-------------------------------------------------------------------------------
دو سیستم OpenAPI هم‌زمان در Program.cs فعال‌اند:

  AddOpenApi() + MapOpenApi()          → /openapi/v1.json   ← سند خالی است
  AddSwaggerGen() + UseSwaggerUI()     → /swagger           ← ۹۰ اندپوینت

اولی سند خالی («paths»: {}) می‌دهد چون کنترلرها با ApiExplorerSettings
به گروه‌هایی مثل Invoice و Ticket تعلق دارند و با نام سند «v1» مطابقت
نمی‌کنند. دومی به‌خاطر DocInclusionPredicate همه را شامل می‌شود.

آدرس درست برای دیدن API:  http://localhost:8080/swagger

پیشنهاد: یکی از این دو حذف شود تا کسی به اشتباه سراغ سند خالی نرود.
